# Against lane: K4.8

**Verdict: adopt with changes.** K4.8 = K4.7 + A only. B goes to a later candidate, and only with its first search call kept out of the loss and with the balance step keyed on search count. As written, B teaches the model to write bad first queries.

1. **B, as built, teaches something else.** A B row and the existing row for the same question have the same context up to the first tool call. One row's target is `query` and the other's is `miss_query`, so the same prompt gets two different first calls. Loss is on the model's decisions, so the first call is trained too, and `miss_query` was chosen on purpose to miss. With several hundred B rows the model learns to make weaker first searches. That works against recall, and the owner's measured failure is already "searches never return the fact" (39 and 34). Fix: mask the loss on B's first call, so only the second call and the reply are trained. If the trainer cannot mask single turns, B should not go in at all (I could not check this from the two files). On never-told: today a second search that returns text ends in a decline 70 times and in a value about 66 times (24 never_told, which is rough, plus 39 and 3). Several hundred B rows would make "second search returned text, so name a value" the pattern the data teaches. K4.7 already named values on Demo2 never-told items that share a word with a stored fact. B makes that more likely, and false retrieval goes up with it. One more gap: the claim "search once, then stop" comes from K4.1 (61 of 66). Count it again on K4.6e2's outside-writer logs on CPU before building B.

2. **Count and place.** No new number. Put B rows before the balance step and change the key in `balance()` from `passages` to `(searches, passages)`. Then two-search rows that end in a value are cut down to round(r x declines) among two-search rows, by the same hashed rule as now. That sets B's count to whatever the existing never-told twice-search declines support (about 94 rows in that cell), not "several hundred". Putting B after the balance step would undo the balance the build exists to keep.

3. **Split. A goes first.** A is the existing rule on more data and targets the diagnosed K4.7 failure (never-told 2 of 4). B is a new mechanism that pushes against never-told. If the two are stacked and K4.8 bombs, there is no way to tell which part did it, and there is no time for a third try. Have the B writers produce output on CPU while K4.8(A) trains. Then K4.9 = K4.8 + B (masked, balanced) is ready as soon as the card is free.

4. **One checkpoint, named now: epoch 2 only.** This matches K4.6e2, the candidate the line now builds on, so the comparison is like for like. If the trainer can stop after epoch 2, it also saves about a third of each seed's time before the Saturday 16:00 ET deadline (the LR schedule stays the 3-epoch one, the same as K4.6e2). Cost: if epoch 3 would have passed, that pass is lost. Epoch 3 only matches the K4.x plan but not the candidate it builds on. Epoch 3, then epoch 2 if 3 bombs, gives two tries at a 10-item gate. A pass then depends on one item twice over, which makes the gate weaker. It would have to be disclosed as a forking path, as K4.6e2 was. The same checkpoint must also be used for seeds 83 and 94.

5. **Tuning to Demo2.** Nothing in B's brief names Demo2 or hard_dev items. However, the reason for A (the "shares a word" diagnosis) and the K4.6e2 checkpoint choice both come from reading Demo2's items. Each K4.x step reacts to the same single writer's 10 items. Keep Demo2 as a pass/fail gate only, with no diagnosis from its items, and disclose that A's motivation came from it.

6. **Prediction, seed 82, as proposed (A + B stacked, epoch 3):** Demo2 older 3 of 6, never-told 2 of 4, hard_dev never_told 44 of 48. For A alone: older 2 of 6, never-told 3 of 4, hard_dev 46 of 48.
